# Spec Review 1: docs 04 (Crypto) and 06 (Sync)

**Date:** 2026-10-09 · **Reviewer:** Claude (self-review of the author's own drafts, so shared blind spots are likely) · **Scope:** `docs/04-crypto-spec.md`, `docs/06-sync-protocol.md`, plus cross-checks against docs 03, 05 and 08.

> This review does **not** replace review by a human cryptographer or the external audit (SEC-R07). It is a first pass to remove defects that would otherwise be baked into code.

**Result: 5 High, 8 Medium, 6 Low findings. All are resolved in the same PR by editing docs 04, 05 and 06.** Section numbers below refer to the updated documents.

Severity: **High** = would cause data loss, a broken core flow, or a real attack if implemented as written. **Medium** = weakens a guarantee or leaves behavior undefined. **Low** = polish, efficiency, or clarity.

## High

| ID | Where | Problem | Resolution |
|---|---|---|---|
| H1 | 04 §5 | `wrap_rk`'s AAD included `header_version`. Changing the master password bumps `header_version`, so `wrap_rk` could no longer verify, and re-creating it needs the recovery key, which the user does not have during a password change. The core "change password without re-encrypting" flow was impossible as written. | Separate AADs per wrap. `wrap_pw` binds `(vault_id, epoch, kdf)`; `wrap_rk` binds only `(vault_id, epoch)`. `header_version` is not in any AAD. |
| H2 | 06 §6 | Segment retry could trigger a **false "fatal integrity alarm"**. If a crash happened after upload but before bookkeeping, new local ops (or a fresh random nonce) made the regenerated segment differ from the uploaded one. Also, "should be impossible" is wrong: **restoring a device backup or cloning a VM reuses `device_id` and `seq`**, creating two writers and breaking the single-writer assumption. | Persist the finished, encrypted segment bytes in a local **outbox** before uploading, so retries send identical bytes. Added §6.1 **fork recovery**: on a mismatch at an existing seq, adopt a new `device_id`, re-emit unconfirmed ops (idempotent), and warn the user. |
| H3 | 06 §5.3 | Conflict detection depended on **arrival order**. If B's edit (based on A's) arrived before A's, A's later arrival looked "concurrent" and created a spurious conflict copy. Copies are persisted items, so they could not be retracted, and merge was no longer order-independent. | Conflicts are now a **derived read-time view** computed from the op graph (base pointers), not created during merge. The user can explicitly "keep as separate note", which is an ordinary op. Merge stays a pure LWW CRDT. |
| H4 | 04 §3/§5 | Header KDF parameters are unauthenticated until after Argon2 runs. A hostile provider could set `m_kib` to many GiB or `t` to a huge value, causing OOM or a hang (denial of service) on any device opening the vault. | Hard **ceilings** as well as floors (m ≤ 1 GiB, t ≤ 10, p ≤ 8), checked before running the KDF, with a UI error rather than an attempt. |
| H5 | 06 §3/§6 | `manifest.bin` was a single overwritable file, so a provider could serve an **older manifest**, hiding truncation or rollback and defeating the rollback detection the threat model relies on (threats 3 and 4). | Manifests are immutable numbered files (`manifest-<counter>.bin`). Each reader remembers the highest counter seen per device and alarms if the provider serves a lower one. |

## Medium

| ID | Where | Problem | Resolution |
|---|---|---|---|
| M1 | 04 §6 / 06 §6 | A provider could copy a valid segment into another device's directory. AEAD passes, and the hash chain of the wrong device is confused. | Envelope `device_id` and `seq` **must equal the file path**; mismatches are rejected and quarantined. |
| M2 | 04 §8 | "Windows Hello-gated DPAPI" is not a real cryptographic gate: `UserConsentVerifier` is only a UI prompt, and plain DPAPI is unlocked by the logged-in session. Malware in the user session could skip the prompt. | Use `KeyCredentialManager` (Hello-bound TPM key); derive the wrapping key from a deterministic signature over a fixed challenge. Linux's Secret Service is documented as **lower assurance**, opt-in, and off by default. |
| M3 | 04 §4/§9 | "Regenerating the recovery key invalidates the old wrap" is false while old `header-*` files still exist in the cloud, since the old RK plus an old header still yields VK. The same holds for an old master password. | Documented honestly: only **VK rotation** truly revokes old credentials. Old headers are deleted promptly, and the UI offers "Change password and rotate keys" when compromise is suspected. |
| M4 | 04 §10 / 06 §8 | Key rotation left gaps: what happens to unsent or already-uploaded old-epoch ops from devices that rotate late, and a revoked device could publish a header with a bigger `header_version`. | New §8.1: devices re-emit ops not covered by the rotation snapshot under the new epoch. Header ordering is `(epoch, header_version, device_id)`, and headers with a lower epoch than known are rejected. |
| M5 | 06 §4 | The HLC section contradicted itself: the receive rule adopts the remote clock, while the text says the local clock "never jumps". | Resolved: always adopt (required for later edits to win), warn above +24 h, and quarantine segments with `pt` more than 1 year ahead as corrupt. |
| M6 | 06 §5.2 | Delete/resurrect semantics were inconsistent with per-field registers: an edit to another field does not touch the `deleted` register. | Defined: an item is visible iff `deleted == false` **or** any field's hlc is greater than `deleted_hlc`. |
| M7 | 06 §3/§11 | Header race: two devices write the same file name `header-<n>`, but the text says "device-specific suffix". The name/ordering rules disagreed. | Header file name is `header-<epoch>-<version>-<device>.bin`. Ordering rule fixed in §11. |
| M8 | 06 §9 | Snapshot `covers` held only `seq`, so a new device could not verify the hash chain after older segments were compacted away. | `covers: device_id → (seq, hash)`. |

## Low

| ID | Where | Problem | Resolution |
|---|---|---|---|
| L1 | 06 §5.1 | 2 s upload debounce creates many tiny segments and leaks edit timing. | Local save stays immediate; **uploads batch ≥15 s**, with an immediate flush on lock or background. |
| L2 | 06 §6 | Manifest rewrite after every download is chatty (quota and battery). | Update the manifest at most every 5 min, or when `seen` advances meaningfully. |
| L3 | 04 §3 | NFKD output can change between Unicode versions, making a correct password fail after a dependency update. | Pin the Unicode normalization crate/version, and add vectors that fail CI on table changes. |
| L4 | 04 §1 | SQLCipher defaults differ across versions and platforms. | Pin `cipher_page_size`, `cipher_compatibility`/version and HMAC settings explicitly, and record them in the DB meta. |
| L5 | 04 §1 | XChaCha20-Poly1305 is not key-committing. | Documented as acceptable: there is no online decryption oracle (no server), so partitioning-oracle attacks do not apply. Revisit if an online component is ever added. |
| L6 | 06 §9 / 05 §7 | Docs disagreed on tombstone lifetime (180 days vs. ack-only). Segments of permanently lost devices are never deleted. | Tombstones are dropped only when acked **and** ≥180 days old. Any device may GC segments of a device inactive >90 days once covered by a snapshot. |

## Things checked and found sound
- Random 192-bit nonces with per-purpose HKDF subkeys: safe at expected volumes.
- Two independent VK wraps (password and recovery key) with a random, non-derived VK.
- The convergence argument for per-field LWW registers, now that conflict handling is no longer part of merge.
- Single-writer layout: with H2's fork recovery, accidental double-writers are handled rather than assumed away.
- Drive `appDataFolder` scope and duplicate-name handling.

## Still open (not resolved here; needs human decision or implementation-time verification)
1. **Whole-vault rollback seen by a brand-new device** is undetectable (documented limitation). A user-held "last known head fingerprint" check could be added later.
2. **Drive/CloudKit behaviors** (consistency of listings after create, `drive.appdata` verification requirements, CloudKit asset limits) were written from memory and must be verified against current docs in the provider spikes (roadmap M0).
3. **Argon2 memory-zeroization** in the chosen crate must be verified (does the library wipe its working memory after hashing?).
4. **Per-device signatures** (attribution and finer revocation) remain deferred.
5. This review should be repeated by a **second, human reviewer** before M1 coding starts.
